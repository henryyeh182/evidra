## Next work that can start now

### 1. Phase 2 - Story 1 closeout：repository lifecycle

優先補齊 durable local repository 的 user controls：

- 定義 backup format 與 restore contract；backup 不應包含不可解讀的 SQLite-only 狀態。
- 定義 deterministic export schema，至少涵蓋 state、plan、decision、outcome 與 provenance metadata。
- 實作 delete／revoke semantics，驗證 raw payload、normalized evidence、token、decision trace 與 outcome records 的刪除範圍。
- 新增 process restart、backup／restore、export、delete 與 user-scope tests。

完成條件：使用者能在 user-controlled environment 讀回、匯出、備份與刪除自己的 private state，且文件能明確說明刪除邊界。

### 2. Phase 2 - Story 3：continuity contract

在現有 `buildDecisionContinuity`／Today Brief 基礎上補完整 contract：

- 固定 `stateId`、evidence window、runtime identity、ingestion source、original writer、platform 與 signal provenance 的 schema。
- 建立最小化 bootstrap payload，證明新對話只取得必要 state／decision context，不重新取得完整健康歷史。
- 補 Garmin → Apple Health chain 的 provenance fixture，以及 HRV 缺失時 `missing` 的明確輸出。
- 加入跨 process／跨 conversation 的 replay、scope isolation 與 stale-state tests。

### 3. Phase 2 - Story 4：private-engine acceptance

以 Story 2／3 的 contract 為輸入，建立五個 acceptance scenario 的端到端 runner：

- local connector／fixture ingestion
- Evidence normalization 與 provenance
- private decision engine
- Today Brief／planned workout adjustment
- privacy boundary assertions（raw Evidence 與 token 不進 hosted path）

每個 scenario 都要驗證 structured decision、action、reason、coverage、missing signals、trace identity 與不洩漏 raw payload；Garmin chain 的 HRV missing 必須是明確可測的 assertion。

### 4. Phase 2 - Story 2：Google Health API OAuth boundary

Story 1 的 delete／token lifecycle contract 定案後，再接 OAuth：

- 最小 scope 與 consent separation。
- token 的 user-controlled encrypted storage。
- refresh、撤銷、刪除與失敗 recovery。
- API response → existing importer／normalizer → Evidence 的 source provenance。
- 明確禁止 refresh token 與長期 raw health history 進 hosted runtime。
